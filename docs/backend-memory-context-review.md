# 记忆机制与 Context Engine 优化审查

> 2026-11-04。审查当前工作区代码；本轮未修改业务逻辑、未调用真实模型、未读取个人数据库。结论来源分为“最小复现”“静态代码确认”“待运行评测”。阅读入口：[结构](backend-code-guide.md)、[算法](backend-algorithm-walkthrough.md)。

## 1. 总体判断与优先级

已有基础值得保留：原文与派生记忆分离、版本化事实、候选确认、画像证据、owner/project 约束、幂等请求、revision 冲突、异步索引、删除失效以及总上下文预算。

优先解决链路一致性，再调模型、阈值和数据库索引。否则不同入口运行不同算法，评测的改进可能根本没有进入真实聊天。

- **P0**：授权和敏感材料使用边界；先完成反例测试与修正。
- **P1**：上下文证据完整性、分支一致性、可观测性和状态语义。
- **P2**：大规模性能、评分校准及重构。规模问题出现之前也可建立基准。

这不是已发生隐私泄露的认定。下列风险按当前代码推导，未验证的真实模型行为明确标注。

## 2. P0：敏感记忆的授权粒度与原文粒度不一致

**代码**：`memory_v2/context_policy.py::allowed/filter_query`；`tools.py::execute(get_source/get_memory_history)`；`runtime.py` 工具结果过滤分支。

**静态确认**：allowed 主要按正则词交集判定。get_source 对选中的 Memory 判权后返回整个 Source.content；一个 Source 可以包含多件事。get_memory_history 先判权所选版本，再返回多个非删除版本；后续 Runtime 主要补做敏感词子集过滤，并没有对每个历史版本完整执行使用策略。

**风险场景**：同一输入里同时描述论文安排和私人财务/第三方情况，只选中论文记忆去读原文；原文中未被有限敏感词表覆盖的内容可能被整体带入。另一个场景是历史版本具有更严格使用策略，却通过较宽松的当前版本读取。

**建议**：建立统一 `authorize_material(owner, scope, purpose, source/version)`。检索、重排、原文、历史、画像及最终上下文均使用同一授权结果。默认返回 Evidence.start/end 对应片段及受控邻近上下文；扩展原文前再检查整段内容。每个历史版本独立判权。对 third_party、private 等结构化标签进行判断，词表只作为补充。

**验收**：构造一份混合 Source，其中有正常信息、标记 private 但不包含关键词的信息和第三方内容；普通记忆原文读取不能带出后两者。较严格历史版本不能从较宽松版本入口绕过。

## 3. P0：画像推断的输入池未限定本人及明确情境

**代码**：`memory_v2/service.py::infer_profiles`（约 464 行）；`MemoryMeta.data`。

**静态确认**：输入池按 owner 和 current 筛选，再检查来源、权限和事件组；没有要求 metadata.subject=self，也没有按 project 明确分组。用户确认保存的第三方事件可以有 event_group_key，从而进入推断材料池。

**影响**：模型可能把“用户记录的他人经历”用于推断用户性格。跨项目证据是否适合汇合也没有显式策略。模型提示词不足以代替材料边界。

**建议**：推断输入显式限制主体；引入 portrait_scope 区分全局稳定偏好与项目限定行为。保留情境与原始主体，禁止自动把第三方事件归为本人；支持证据和反对证据都检查主体、有效性、许可及版本。

**验收**：三次、跨两天记录同学行为，不得满足本人性格推断门槛；同一事件重复讲述不算三次独立经历。跨项目画像须符合明确配置的汇合规则。

## 4. P1：事实、画像和来源共用去重空间，详细证据可能丢失

**代码**：`memory_v2/context_policy.py::ContextPlan.select`（约 126 行）；`tools.py` 的 get_source 输出；`runtime.py` evidence 字典。

**已最小复现**，未连接数据库：

| 输入顺序 | 结果 |
| --- | --- |
| 已选择 Memory m1/fact f1，再给两个来源 s1/s2，二者 id 都是 m1 | 两个原文只选中一个 |
| 再次请求同一来源 | 被判 duplicate |
| 先选 Profile p1/fact f1，再选 Memory m1/fact f1 | 详细事实被全部过滤 |

注意：Memory 的去重键通常是 fact_id，而 source 输出只有 id；因此不是所有“先检索后查原文”都会得到空结果。问题在于表示层级混用、多个来源 ID 冲突，以及无法从摘要升级到细节。

**建议**：将材料标识改为类型化键：`profile:id:revision`、`memory:id:version`、`source:id:span`。事实身份用于关联与内容去重，不直接等同于材料身份。需要原文时，用详细表示替换摘要并计算预算差额；多个来源保留独立引用 ID。

**验收**：先注入画像再查事实仍能得到事实证据；一个记忆对应两个来源可逐个读取；重复查原文不重复计费，但应返回 already_provided 或证据定位，不能让模型误以为不存在。

## 5. P1：新旧写入入口行为不同

**代码**：`tools.py::execute(propose_memory)`（约 199 行）；`memory.py::enqueue`（约 90 行）；`runtime.py` 回答完成后的自动写入。

**静态确认**：工具仍调用旧 MemoryService.enqueue(automatic=True)。旧服务遇到会话已有 V2 Policy 时直接返回 None；而回答成功后的路径会按 V2 Policy 调用 MemoryV2.enqueue。

**影响**：授权已开启时，工具可能返回“智能记忆关闭”，随后回答完成又创建新版任务。若回答失败或取消，工具请求与自动提交的结果也可能不一致。没有会话 Policy 时还存在 legacy 兼容路径。

**建议**：抽出统一 MemoryWriteCoordinator，显式区分 explicit/automatic/tool_request；所有入口共享授权、幂等键与任务结果。旧版兼容作为明确模式；工具结果应区分未授权、跳过、已存在、已排队，而不是把所有 None 解释成关闭。

**验收**：会话 on/off/legacy × 全局开关 × skip × 工具调用 × 回答成功/失败的矩阵测试；同一消息至多一个有效提取任务，回执真实一致。

## 6. P1：检索分支和预算存在交叉配置问题

**代码**：`retrieval.py::search`（约 47 行）；`runtime.py` 中 v2 与 plan 分支；`context_budget.py`。

**静态确认**：新版记忆启用时不会进入实验 search_v2，因此实验阈值、缓存、候选诊断未全部进入主链路。若两个开关同时启用，Runtime 的部分旧 MemoryBudget 分支仍会执行，形成 ContextPlan 之外的额外裁剪；预检索提示也可能在未实际预检索时宣称证据不足。

**建议**：用显式 PipelineConfig 表达写入版本、检索算法和授权策略；上下文预算只保留一个权威账本。统一检索 pipeline 为：范围过滤 → 使用授权 → 多路召回 → 阈值/重排 → 去重/多样性 → 预算组装。实验方案通过参数选择，授权约束不能随实验消失。

**验收**：四种开关组合明确得到哪条路径；trace 记录实际 retrieval_strategy；单份材料只预算一次，零预算禁用个人长期记忆；没有执行预检索时不得输出预检索失败提示。

## 7. P1：最终复核没有覆盖全部已注入依据

**代码**：`runtime.py` 约 403–418、472 行及最终消息持久化分支。

**静态确认**：selected_profiles 被加进 system，但 evidence 初始只包含 core。在 V2 路径 core 为空；如果回答只依据画像，可能不进入有 evidence 才执行的 GROUNDING 复核。画像 ID 引用也可能被当作未知引用。后续 GROUNDING 请求没有经过 ContextPlan.fit；而主模型调用后的 epoch 检查发生在这次复核调用之前。

**风险**：审校看不到模型实际使用的全部依据；长材料的第二次模型调用不受同一预算约束；复核期间发生记忆变化可能错过最终提交前的同等校验。

**建议**：所有实际注入项进入统一 EvidenceRegistry，标记来源类型、版本、权限、注入位置与可引用性。每次模型调用，包括摘要、审校，都经过预算器；最终写入回答的事务重新校验依赖版本/epoch。优先按实际被选材料依赖校验，而非无限扩大到整个 owner。

**验收**：只有画像依据的回答可正确追溯；在审校模型等待期间删除相关记忆，回答不能继续保存旧事实；长证据输入下审校也不超预算。

## 8. P1：状态字段已保存，但部分执行语义缺失

**代码**：`ContextPlan.profiles()`、`effective_options()`、`context.py::build`、`context_router.py`、`config.py`。

| 字段/能力 | 当前情况 | 建议 |
| --- | --- | --- |
| pinned | 可保存，画像选择不使用其排序 | 在授权、相关性通过后有限加权；不能绕过预算或敏感许可 |
| history_scope | 可保存，未按近期/阶段/全历史区别选材 | 接入 HistorySelector，或标记暂不支持 |
| memory_write_debounce_seconds | 配置存在，无对应防抖执行逻辑 | 实现消息聚合与取消/授权变化检查，或移除误导配置 |
| do_not_mention | 更新时可撤销跟进，但 allowed() 不直接以该字段分支 | 明确主动提及、话题延续、显式回忆三种目的，再执行策略表 |
| detail_level=summary | 没有通用的内容抽象/脱敏器；召回仍可能是完整 Memory.content | 把“允许使用”和“允许展示多少细节”拆成授权与材料变换两步 |
| temporal_status | 完整值存 metadata，主要检索返回未带完整语义 | 返回事件状态与有效时间；取消计划不被当作当前待办 |

**验收**：同一场景只改变一个字段，实际上下文变化必须符合定义。若无执行差异，接口应如实报告支持能力。

## 9. P1：短期工作记忆尚不能支撑长期项目推进

**代码**：`update_working_state/working_state_view`；`context.py`；`service.py::invalidate`。

当前 WorkingState 每轮覆盖最新主题和情绪；过期处理只在读取视图中。Runtime 未把该状态作为持续规划输入。新版历史只保留有限近期轮次，禁用旧摘要；因此重要约束、未决问题、临时承诺可能随窗口消失。

**建议**：增加带证据的结构化工作状态：current_goal、constraints、open_questions、temporary_plan、emotion_context。每条带 source_message_ids、更新时间、有效期与适用情境；更新采用合并/撤销而非整块覆盖。用规则控制状态寿命，用模型辅助抽取；当前原话优先于旧状态。

**验收**：长对话后仍记住用户明确约束；已取消计划不复活；一次“好累”不会成为稳定画像；情绪过期后不继续当作当前状态。

## 10. P2：事实身份和证据独立性需要更稳健

**代码**：`claim_key`、`commit`、`infer_profiles`。

当前 fact 身份依赖模型输出的 subject/predicate/context 字符串；episode 身份依赖 source；event_group_key 依赖模型时间；画像门槛使用来源创建日期。结果可能是语义同一事实产生多个身份，或独立事件被误合并。

建议建立受控 predicate 字典、主体实体 ID、事实适用范围和事件实体；语义相似只产生“可能同一事实/事件”的候选，不自动覆盖。区分发生时间、用户叙述时间、入库时间。支持反证后暂停、降权或重新确认，并记录为什么变更。

验收使用改写、跨天重复叙述、同名人物、不同项目同一偏好、同一天多个事件等数据。先评估错误合并率，再调整阈值。

## 11. P2：查询规模与实际索引

**静态确认**：仓库未见 HNSW/IVFFlat/GIN 建索引 SQL；存在 `index=True` 和 UniqueConstraint。仅根据源码不能判断运行数据库是否手工创建过其他索引。

性能关注点：

- 主检索关键词只扫描最近 2000 条，较早且未生成向量的有效记忆可能永远失去召回机会。
- filter_query 加载敏感候选，逐条再查询 metadata/policy；画像循环逐条读取依据，有 N+1 查询风险。
- 实验检索每次计算全量版本摘要作为缓存版本，成本随库增长。
- 单 worker 顺序执行提取、索引、画像；昂贵画像任务可能阻塞其余任务。
- Database.migrate() 以 create_all 和有限版本分支为主，不是完整、可回滚的逐版本迁移系统。

**建议先测再建**：

| 访问模式 | 候选优化方向 | 验证 |
| --- | --- | --- |
| owner/project/status + 最近排序 | 组合 B-tree，按真实 WHERE/ORDER BY 设计 | EXPLAIN ANALYZE，扫描行数和排序成本 |
| QUEUED Job 按时间领取 | state/created 或 QUEUED 部分索引 | 队列增长下领取延迟 |
| profile owner/state/category | 组合索引、批量加载证据/策略 | 每次请求 SQL 数量 |
| 内容关键词检索 | 选择并验证中文分词/倒排或 trigram 路线 | 中文 Recall@K；不直接假定英文全文配置适用 |
| 大规模向量检索 | 评估固定维度和模型隔离，再选择 ANN 索引 | 对比精确 cosine 基线，过滤后的召回与 P95 |
| 删除依赖传播 | 规范化证据依赖关系及反向索引 | 删除影响范围和传播完成时间 |

1 千/1 万/10 万条合成数据只是起始档位，需覆盖单用户倾斜、项目过滤、并发更新和删除。本文未执行性能压测，不能给出加速倍数。

## 12. P2：预算和可观测性统一

当前预算估算混有 UTF-8 字节、字符上限和配置名中的 tokens；保守估算有价值，但跨模块含义不够统一。`trace.context.summary_used` 还根据数据库存在有效 Summary 判断，而 V2 实际不注入旧 Summary，可能误报。

建议拆分 requested/effective/actual 三层配置；用可替换 tokenizer adapter，先用真实调用 usage 校准估计误差；保留模型上下文安全余量。trace 应直接来自最终实际 messages/material ledger，记录被过滤和被裁剪的原因，不根据数据库存在性推测“已使用”。

不要记录内部思维链；记录可验证的输入材料 ID、版本、选择理由、预算、工具行为和引用足够定位问题。调试正文记录须有保留期限与删除联动。

## 13. 建议实施顺序与验收门槛

### 阶段 A：统一正确性边界

统一写入协调器、材料授权、类型化材料 ID 与最终持久化检查。用程序断言验证：候选未确认不能变事实；第三方不能成为本人画像；删除不能被来源/历史/缓存复活；预算零不能注入个人长期记忆。

### 阶段 B：完善 Context Engine

统一预算与 EvidenceRegistry，接通 pinned/history_scope、结构化工作状态和事实时间语义。建立可回放 trace，能区分“库中存在”“检索候选”“实际注入”“最终引用”。

### 阶段 C：真实质量评测

冻结多阶段生活/学习/项目场景，比较无长期记忆、简单检索、完整策略及消融版本。分别评估提取准确率、错误写入率、检索召回/精度、上下文冗余、不当敏感重提和个性化收益。真实模型需重复运行，保留模型/提示词/配置版本。

### 阶段 D：数据库与任务优化

基于 PostgreSQL 计划和规模数据决定索引；再处理任务租约、批处理、重试退避和公平调度。保留当前单 worker 作为简单部署模式，但不要把它误认为可水平扩展设计。

## 14. 本轮检查边界

完成了文件/关键调用路径核对、字段使用搜索、仓库索引定义搜索，以及 ContextPlan 去重的两个最小复现。未运行真实模型质量评测、未运行数据库索引基准、未验证所有并发时序、未修改后端代码。上述建议应先转成可失败的场景，再实施修复，避免靠主观调参判断效果。
